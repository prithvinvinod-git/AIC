Comprehensive Codebase Summary: servox-phi (servox/AIC)
1. The Complete Current State Machine Flow (from src/lib/issueMachine.ts)
The authoritative transition table is TRANSITION_RULES, executed transactionally by applyTransition(). Important: The machine in the code has evolved beyond what CONTEXT.md and docs/app_status.md (v4.0) describe. There are now 14 statuses and two new head roles.
Statuses (from types.ts):
NEW → VALIDATED → ESCALATED → APPROVED → ROUTED → PENDING_ASSIGN → ASSIGNED → ONGOING → PENDING → COMPLETED → INSPECTED → VERIFIED → CLOSED plus REJECTED (terminal).
Full transition table:

Cascade behavior (applyTransition switch):
- VALIDATED P1–2 → auto ESCALATED (sets escalation = {required:true, status:"pending"}), two timeline entries.
- VALIDATED P3–5 → auto ROUTED to maintenance head (denormalizes routing.maintenanceHeadUid), two timeline entries.
- INSPECTED → always sets verification block and auto-transitions to VERIFIED with an auto timeline entry.
- COMPLETED set via complete → does NOT cascade; stays COMPLETED awaiting category-head inspection.
- SLA init: initSla at APPROVED (P1–2) or ASSIGNED (P3–5); paused on PENDING (pausedAt, totalPausedMs); resumed/extended on ASSIGNED.
2. Roles and What They Can Do at Each Status
Roles (types.ts): reporter, validator, hod, principal, maintenance_head, category_head, maintenance, purchase, admin.
- reporter: creates issues (POST /api/issues); rates VERIFIED → CLOSED (0.5–5). Comments. Sees own issues.
- validator (department-scoped): NEW→VALIDATED/REJECTED; VALIDATED→ESCALATED/ROUTED/ASSIGNED; APPROVED→ROUTED; ASSIGNED/ONGOING→PENDING; ONGOING→COMPLETED; PENDING→ASSIGNED. No longer verifies COMPLETED (this changed — see inconsistencies).
- hod / principal: ESCALATED→APPROVED/REJECTED (approve with severity revision).
- maintenance_head: ROUTED→PENDING_ASSIGN (forward to category head) or ROUTED→ASSIGNED; PENDING_ASSIGN→ASSIGNED.
- category_head: PENDING_ASSIGN→ASSIGNED (assign team+workers); COMPLETED→INSPECTED (on-site verification, auto→VERIFIED) or COMPLETED→ONGOING (send back). Scoped to own routing.categoryHeadUid.
- maintenance: ASSIGNED→ONGOING (must be assigned staff); ASSIGNED/ONGOING→PENDING; ONGOING→COMPLETED.
- purchase: not in the status machine. Approves/rejects needsApproval requirements (with price / reason), auto-resolving them.
- admin: allowed on nearly all transitions as an override.
3. All API Endpoints

- POST /api/issues — create NEW (reporter only), after(): AI triage + duplicates, notify validator, stats, reported email.
- GET /api/issues?status=&mine=&scope=board — role-scoped lists; scope=board returns P1–3 across all depts (max 10, minus boardHidden).
- GET /api/issues/[id] — issue + timeline + comments + attachments.

- POST /approve (→APPROVED)
- POST /forward (→ROUTED or PENDING_ASSIGN; resolves maintenance head / category head + name)

- POST /complete (→COMPLETED)
- POST /inspect (→INSPECTED, category head)

5. Inconsistencies & Issues Noticed
 1. Documentation is badly out of date relative to the code. CONTEXT.md and docs/app_status.md (v4.0) describe the validator-only model (no maintenance_head/category_head, no ROUTED/PENDING_ASSIGN/INSPECTED, head merged into validator, COMPLETED → VERIFIED by validator). But the actual code has re-introduced two head roles and three new statuses, moved completion verification to the category head, and changed the route. The docs do not match the implemented machine.
 2. The /verify endpoint is now effectively dead. COMPLETED has no → VERIFIED transition rule for any role (only INSPECTED/ONGOING by category_head/admin). The generic POST /verify route would always fail from COMPLETED. The current UI routes category-head verification through /inspect (which cascades to VERIFIED). VerifyCard in HeadCards.tsx still calls /verify and is an unused export (dead code).
 3. AssignCard is also unused (dead code in HeadCards.tsx); only RouteToHeadCard is imported/used (board page).
 4. Smoke test is out of date (scripts/smoke-lifecycle.mjs): it drives the old APPROVED → ASSIGNED (validator assign) and COMPLETED → VERIFIED (validator verify) path. Under the current machine, P2 validate auto-escalates (still OK), but there is no COMPLETED → VERIFIED transition, so step 7 would fail, and step 4's direct /assign from APPROVED is no longer the normal flow (needs ROUTED→PENDING_ASSIGN via heads).
 5. firestore.rules issues.update is stale/incomplete for the new flow. It only authorizes specific role→status combinations (e.g. validator on ['COMPLETED','PENDING','ASSIGNED'], maintenance on ['ASSIGNED','ONGOING']). It does not include maintenance_head, category_head, or the ROUTED/PENDING_ASSIGN/INSPECTED statuses. Since all writes go through route handlers (defense-in-depth), this is flagged as "harmless/stale" but would block any direct client writes in the new flow. It also still references the removed head pattern implicitly (no head literal now — actually rules only mention validator/hod/principal/maintenance/admin).
 6. Rating schema mismatch: feedbackSchema/feedback route enforces rating: 0.5–5, multipleOf(0.5); the machine's CLOSED check matches (0.5–5, half steps). But statusTransitionSchema (generic door) enforces rating: int 1–5 — so if someone closes via the generic /status endpoint (used by AssignedActions? no—only ONGOING via generic), half-step ratings would be rejected. CloseIssueModal/StarPicker allow 0.5 steps. Minor inconsistency between the generic door and the dedicated feedback door.
 7. HEAD_ROLES nav label: nav.ts maps both maintenance_head and category_head to /dispatch, which correctly distinguishes tabs. ROLE_HOME maps all roles to / (landing decides), consistent with docs.
 8. Board page (validator) still reflects old flows: It shows a "Route queue" of APPROVED issues and "Blocked" PENDING issues rendered via RouteToHeadCard (forwarding to head). It has no explicit section for the new ROUTED/PENDING_ASSIGN/INSPECTED statuses, though the machine now produces them. The validator board does not render a verify panel for COMPLETED (correct under new rules) but the UI messaging still says "verify completed jobs."
 9. routing.staff name-lookup inside applyTransition ASSIGNED uses tx.get inside the transaction — allowed, but unusual; works.
10. Push notification FCM code exists in both notifications.ts and functions/src/index.ts; TYPE_META in constants.ts includes purchase and sla/reminder/digest types referenced by functions not all present in NotificationType union in types.ts (minor typing gap).
11. Emails: transition.ts fires sendFeedbackEmail on CLOSED, sendJobAssignmentEmail on ASSIGNED, sendIssueApprovedEmail on APPROVED (all best-effort, gated by EMAIL_ENABLED). Rejection never emails. Reported email fired on create with AI-priority preference. Templates use the warm terracotta theme (contrary to docs/app_status.md §8 which claims a "dark ChatGPT-style" theme — docs inconsistency; actual templates in templates.ts are the warm "Claude" theme as CONTEXT.md says).
12. Auto-close: docs/app_status.md §16 says it's a pending gap, but CONTEXT.md §9 says it's implemented via GET /api/cron/auto-close (Vercel cron daily). There is a src/app/api/cron/auto-close/ directory — so it is implemented, contradicting app_status.md. src/lib/autoClose.ts exists.
